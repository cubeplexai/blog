In July 2026, Y Combinator published [QM (Quartermaster)](https://github.com/yc-software/qm), the multiplayer agent harness it uses internally, under the MIT license in `yc-software/qm`. The public repository was created on 2026-07-29. This article is pinned to commit `95b5a6a`.

QM is built for startups: each employee gets an isolated work site; when they need to collaborate, they work with the agent in channels, group messages, and projects. Boundaries default to person and room; sharing requires an explicit grant. Hand a personal assistant to a whole company and memory, credentials, and side effects tangle. QM's collaboration model starts from that fact.

## Where a personal assistant breaks at company scale

A personal assistant is usually tied to one person's chat, local directories, and login state. Sharing that site across many people creates collisions quickly.

Project knowledge and personal preference land in the same memory and files, so ownership is unclear later. Credentials that enter a shared execution environment are hard to attribute. Channel work still needs shared context; rebuilding the scene per person is expensive. The company also needs a controlled set of models and harnesses, plus auditable side effects.

The README frames QM as a multiplayer harness for startups: people work independently without stepping on each other, and they can also collaborate in channels, groups, and projects.

## Collaboration model: personal sites and room meetups

QM represents work boundaries as scopes: personal, channel, team, org, and group. Projects map onto a group-style scope. Each person and each room can own its own memory, files, keychain view, permissions, crons, web apps, and durable sandbox.

Full sites are not shared by default. Skills belong to a scope and move by grant; promotion to the whole org is admin-gated. People can customize the agent as theirs and still use the same identity and configuration in Slack channels and projects. Identity carries between Slack and the web.

The security story matches local coding agents such as OpenCode, Codex, and Claude Code: the agent acts as the person it works for, with that person's credentials and permissions, and actions are audited. The org picks one security posture; narrower scopes can only tighten it. Command policy applies in every posture. The threat model, operator assumptions, and known limits live in `SECURITY.md`.

## Architecture that follows

Those collaboration cuts show up in a few implementation choices.

Turns run through a headless core: identity, policy, scheduler, and the agent loop, with Postgres for durable state. Pi, OpenCode, Codex, and Claude Code can all drive the same core. The agent has a small, fixed tool surface; `execute` runs commands in that scope's own isolated sandbox — its durable computer, where installed tools stay installed.

The web UI, admin panel, and public portal are optional plugins over the core HTTP API. Slack is an optional in-process plugin that core starts and supervises. The generic core stays company-agnostic; org config, custom tools and skills, sandbox image, and infrastructure live in a deployment directory that `qm init` places in the operator's own cloud account.

The browser path is separate from shell gates: actions inside the browser runner do not re-enter command policy or human approval. They rely on task-level consent and spend checks, and traffic exits through the browser provider rather than QM's egress proxy.

## Limits stated in SECURITY.md

QM describes itself as early, experimental software — not a hardened public or multi-tenant service boundary. Known limits include bypassable command policy (obfuscation, encoding, or write-then-execute), which the docs call a speed bump; plaintext credentials while in use inside a sandbox; incomplete, heuristic content screening; and admin read access to sensitive content (audited, without a separate consent step).

A deployment still needs its own security and operations review. Design goals in the docs are not delivered guarantees.

Teams that already live in Slack, can operate in their own cloud, and accept experimental software can start from an org-owned deployment repository that depends on `@yc-software/qm` and the in-repo deployment docs. This article is not a setup tutorial.
