QM and CubePlex address the same problem: once an agent serves more than one person, how can a team share work without mixing permissions, context, and runtime environments? They start in different places. QM grew out of YC's experience operating a fleet of personal agents. CubePlex treats the workspace as the basic unit of team work. This article compares public designs and current implementation, and does not present unshipped Managed Agent work as a product capability.

## Two collaboration units

QM's [launch note](https://qm.ycombinator.com/) describes YC's path: a Ruby agent loop gained crons and webhooks, then more than 50 Hermes personal agents were provisioned for employees. Managing the fleet became difficult. QM answers with scopes. Personal, channel, team, organization, group, and project work occupy distinct scopes; each person and each room can have its own memory, files, keychain view, permissions, crons, web apps, and durable sandbox.

QM keeps a personal agent personal while allowing it to participate in channels and projects. A skill belongs to one scope and reaches another only through a grant; an administrator decides whether it becomes organization-wide. The organization can choose a security posture, models, and harnesses without receiving default access to every personal environment.

CubePlex's public documentation puts organizations, workspaces, roles, and model-access policy in one team-governance model. A workspace sandbox preserves files, packages, and the working tree across restarts; memory can be personal, workspace-scoped, or organization-scoped; MCP connectors are granted per workspace. The center of gravity is a team workspace that accumulates files, skills, memory, and deliverables, rather than a personal agent computer.

Both designs avoid putting all context into one company-wide agent, but sharing starts at a different point. QM protects personal and room boundaries first, then spreads resources by grant. CubePlex provides an organization-governed workspace first, then brings personal and organization memory into the same work flow. That is a product-design emphasis, not a claim that either model is inherently safer.

## Where governance lives

QM's core owns identity, policy, scheduling, and the agent loop. Company-specific configuration, tools, skills, sandbox images, and infrastructure live in a deployment directory in the operator's cloud account. The README also defines a private-fork workflow: private material remains in `deploy/layers/`, generic core follows upstream, `update-qm` opens sync PRs, and `upstream-pr` returns organization-neutral fixes to the community.

CubePlex is delivered differently. The same product can be self-hosted with Docker Compose or Kubernetes, while the platform provides organizations, workspaces, roles, model-access policy, and cost tracking. Teams with one platform operation model, multiple IM entry points, and a shared connector catalog may avoid maintaining a QM deployment repository for each organization. Teams that want runtime images and organization customizations to live long-term in their own fork may find QM's deployment boundary more direct.

The comparison centers on organization customization and team governance. QM treats organization customization as deployment assets outside an open-source core. CubePlex makes team governance a first-class platform concern. A team should decide who operates the runtime, manages shared tools, and approves organization-level changes before choosing its collaboration unit.

## Runtime and sandbox boundaries

Neither system treats a sandbox as the complete definition of an agent. QM's headless core holds the API, identity, policy, scheduler, and agent loop; `execute` sends commands into the relevant scope's sandbox. The sandbox retains installed tools and working files, but not the model loop.

CubePlex's current README describes an Agent runtime built on CubePi for multi-model access, tool execution, streaming, middleware, and durable checkpoints. Its workspace sandbox is an isolated execution environment with persistent working state. The current backend also shows `RunManager` constructing and driving a CubePi agent in the service, then passing a sandbox as an execution dependency. This keeps sessions, approvals, and streamed events from depending on one shell process while retaining long-lived workspace files and packages.

The shared architecture is meaningful: model loops, identities, and policy live on a governable side; sandboxes run constrained file, command, and browser work. QM ties a sandbox to a personal or room scope. CubePlex preserves work in a workspace sandbox. A real deployment still needs to evaluate egress, credential injection, browser paths, and audit retention; component names are not enough.

## Current capabilities and future design

QM's SECURITY.md calls it early, experimental software rather than a hardened public or multi-tenant boundary. Its command policy can be evaded by obfuscation, encoding, or write-then-execute patterns; credentials in active use in a sandbox are plaintext; browser-runner actions do not re-enter command policy or human approval. These are current public limits, not details the scope model removes.

CubePlex currently provides workspace sandboxes, personal/workspace/organization memory, workspace-granted MCP connectors, automation triggers, and several IM bridges. Its trigger pipeline currently runs only the `inline` target; a `target_type=managed_agent` returns “not implemented.” Long-lived, reusable Managed Agents that can wake from triggers remain an architectural direction worth discussing, but not a released CubePlex capability.

## Conclusion

QM suits organizations extending personal agents into collaboration: personal environments stay distinct, channels and projects share only what they need, and the deployment repository is itself a maintenance boundary. CubePlex suits teams placing agents in an existing workspace: shared sandboxes, memory, skills, MCP, and deliverables sit in one platform alongside roles, model policy, cost, and multiple collaboration surfaces.

This is an author judgment based on current public material and source, not a ranking of performance, security, or completeness. Before choosing, map who owns the team's workspace, personal context, credentials, and runtime. That usually matters more than which agent appears stronger in a demo.
