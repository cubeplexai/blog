QM (Quartermaster) is YC's open-source, self-hosted multiplayer agent harness. It places people, Slack channels, groups, and projects in scopes, using each scope as an agent work environment and permission boundary. CubePlex is an open-source Agent Workspace for teams: it first defines a long-lived Workspace Agent, then lets Web, Slack, Discord, Microsoft Teams, Feishu/Lark, DingTalk, WeCom, and other entry points determine the conversation, identity, and execution boundary for a run.

The distinction changes everyday use. One model is suited to operating many independent agent computers under a company's permission and runtime system. The other is suited to keeping one team agent consistent across entry points without mixing private conversations, credentials, or execution environments.

## A QM scope is an environment and permission boundary

QM currently defines personal, channel, team, organization, and group scopes. A Slack DM enters a personal scope; a channel uses a channel scope; a Slack multi-person DM enters a group scope. A project is also implemented as a group scope and can be linked to a Slack home channel: channel members become project members, and the channel becomes the default delivery audience for scheduled work and reports.

Scope is more than a UI category. QM uses it to determine who can enter an environment, which file layers are visible, how credentials are granted, and which durable sandbox receives a command. A channel scope lets channel members work against shared context without bringing another employee's files or credentials into the run. Organization, current-scope, and personal-scope layers can all take part in resolution, with different read/write boundaries.

This model suits teams that operate agents as a fleet of configurable work computers. They can prepare distinct environments, files, and access relationships for separate scopes and use Slack's people and channel structure directly in their agent-boundary model. When channels, projects, or groups need different tools and runtimes, their configuration is maintained per scope as well.

## A CubePlex Workspace defines the long-lived agent

In CubePlex, a workspace is both a collaboration unit and the boundary for reusable agent configuration. Its AgentConfig stores the workspace persona; skills are attached through workspace bindings; MCP connector state belongs to the workspace. A member working from the web or an IM entry point meets the same role definition and baseline tool set, rather than a new agent configuration because they entered a different Slack channel.

That has a direct team benefit. A research, release, or engineering assistant can retain a stable responsibility, instruction set, and skills. The team does not need to recreate its persona, skills, and MCP connector setup in every channel where that assistant appears. Workspace memory can retain project facts, procedures, and decisions so the next piece of work starts with existing team context instead of a new channel scope.

It does not put every state item into a shared workspace pool. CubePlex memory has personal, workspace, and organization layers: personal memory holds one member's preferences and corrections within the current workspace; workspace memory holds team-reusable facts and procedures; organization memory holds organization-wide knowledge. An MCP connector can be enabled in a workspace while its credential grant remains organization-, workspace-, or user-scoped. A team can therefore use one GitHub MCP without sharing every member's GitHub identity.

## A chat entry point determines the run boundary

This article uses Slack because QM derives scopes directly from Slack DMs, channels, and multi-person DMs. CubePlex IM bridges also support Slack, Discord, Microsoft Teams, Feishu/Lark, DingTalk, and WeCom. Once an entry point is attached to a workspace, CubePlex does not create a separate set of agent capabilities for every IM location; it constructs a conversation boundary from the entry point instead.

- A DM is always one-to-one. Even a bot configured for shared routing keeps the member's own topic, personal memory, and human-in-the-loop identity in a direct message.
- Group chats can use shared or isolated routing. Shared routing gives participants in a channel one common conversation; isolated routing keeps a distinct conversation context for each participant in the same channel.
- This routing setting currently applies uniformly to a bot account, rather than being configured channel by channel. Individual channels remain distinguished by their Slack channel IDs.

Execution follows the same principle. A CubePlex Sandbox record is bound to an organization, a workspace, and a scope tuple. That tuple may represent a user, conversation, or topic. The workspace reuses the agent definition and resource configuration, while the actual run can still be isolated by person or collaboration context.

The same bot therefore has a consistent persona, skill set, and team knowledge at every entry point, but it should not produce mechanically identical answers. Direct-message history, personal preferences, and user authorization differ from a shared group discussion and its visible permissions. A stable agent identity with controlled context differences is the combination team work requires.

## Reuse configuration while preserving isolation

QM's default composition begins by identifying a scope from Slack or project context, then establishes the corresponding resources and access relationships. CubePlex begins by establishing a Workspace Agent, then maps IM entry points to conversation and execution boundaries.

| Team concern | QM | CubePlex |
| --- | --- | --- |
| Long-lived agent definition | Organized separately by personal, channel, group, or project scope | Persona, skills, workspace connectors, and team memory are reused in one workspace |
| Slack direct message | Routes to a personal scope | Keeps a one-to-one conversation, personal memory, and user identity |
| Slack group chat | Routes to a channel or group scope | One bot can use shared context or isolate context by participant |
| Execution environment | A durable sandbox corresponds to the scope | A sandbox can bind to a user, conversation, or topic within the workspace |
| Connector authentication | Determined by scopes and grant relationships | Connectors can be reused by a workspace; credentials can be granted to an organization, workspace, or user |

QM gives explicit product meaning to project scopes, Slack-roster linkage, and scope-level environment organization. CubePlex uses a different default composition: it concentrates a team agent's long-lived definition in the workspace, then handles entry-point differences through conversation, identity, permission, and execution boundaries. For teams that want one stable team agent in multiple collaboration surfaces without maintaining a separate agent configuration for every channel, that composition more closely matches their daily work.

## Team deliverables remain in the workspace

Research, release preparation, and customer proposals are rarely one conversation. Members add material, review results, connect systems, and later continue editing documents, code, spreadsheets, or images. CubePlex keeps this work in a workspace: members and roles control participation, artifacts retain files, previews, and generated output, workspace memory retains reusable facts, and sandboxes provide execution state for a particular user, conversation, or topic.

Teams do not have to choose between a shared bot with no boundaries and copying an agent computer into every Slack location. One workspace can hold long-lived agent capabilities while each entry point retains its appropriate privacy, permissions, and run context.
