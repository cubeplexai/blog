QM establishes an important point: company agents cannot be personal assistants sharing one Slack bot. After YC had deployed dozens of personal agents internally, QM placed memory, files, credential views, permissions, schedules, and durable sandboxes inside scopes. A person, channel, project, and organization each have a boundary; sharing happens through grants. It answers the problem of operating many agent computers inside one company.

CubePlex starts elsewhere. Teams rarely lack an agent that can run a command. They lack a place where work can keep moving: research, connector access, working files, and intermediate output must remain usable when a member changes, an entry point changes, or the next task begins. CubePlex therefore makes the workspace—not an individual agent computer—the unit of collaboration.

## QM defines the boundary of an agent fleet

QM's scope model is serious and necessary. An employee's personal agent should not receive default access to colleagues' files or credentials. A channel needs shared context without acquiring everybody's environment. QM's headless core owns identity, policy, scheduling, and the agent loop; `execute` sends commands into the relevant scope's durable sandbox. Slack, the web interface, and the admin interface are surfaces over that core.

That lets a technical team operate agents as a fleet of customizable work computers. Organization-specific tools, skills, sandbox images, and infrastructure live in a deployment directory. A team that needs deep customization can maintain a private fork while keeping core aligned with upstream. This is compelling for companies that already have platform engineering and want runtime and organization customization to remain in their own repository.

It also makes the adoption cost explicit. Deploying QM is not installing a chat application: a team has to own the cloud account, identity, model credentials, networking, images, upgrades, and incident response. QM's public README positions it as a self-hosted harness for startups. Its Kubernetes sandbox backend remains an open PR whose description says live-cluster validation is still outstanding. Contemporary PRs and issues are still refining external-content screening, credential delivery, and audit records. This is not a claim that one product is more advanced. It is the practical question: is the company prepared to operate an agent fleet?

## Team work should outlive an individual agent

Competitive research, launch preparation, and a customer proposal usually pass through several people. One person starts the work from Feishu or the web, another adds source material, an agent checks repositories, documents, and web pages, and someone reviews a document, spreadsheet, image, or code change. What must persist is not one agent's conversation. It is the context and result of the work.

CubePlex holds that set of assets in one workspace. Members and roles determine who participates. The workspace sandbox preserves files, packages, and the working tree. Personal, workspace, and organization memory separate individual preferences, team facts, and organization knowledge. MCP connectors are granted per workspace. Files, previews, code, and images are retained as artifacts in the thread. The team can continue the same work when a member leaves, the entry point changes, or the next task starts.

That does not pool all data into a company-wide agent. Personal memory remains personal, and a connector must still be explicitly granted to a workspace. The difference is that a workspace for a piece of team work is the default shared object, rather than a collection of personal or room scopes whose sharing relationships are assembled one at a time.

## Runtime is an execution resource, not the owner of collaboration

Both systems separate sandboxes from the model loop. QM makes each scope's sandbox that scope's durable computer. CubePlex's Agent runtime is built on CubePi and handles multi-model access, tool execution, streaming, middleware, and durable checkpoints in the service; a workspace sandbox retains the execution state. In v0.7.2, `RunManager` constructs and drives the agent in the service, then passes the sandbox as an execution dependency.

That choice changes daily team work. Binding a sandbox to a person or channel suits an organization that wants every scope to own a separate computer. Binding one to a workspace suits a project group that needs to preserve its code, source material, skills, and outputs. CubePlex can run on Docker Compose or Kubernetes, while providing workspace, role, model-policy, cost-tracking, and multi-surface collaboration without requiring a QM deployment repository for every organization.

CubePlex provides scheduled and webhook automation triggers. Its current trigger pipeline runs only `inline` targets; `managed_agent` targets are not yet implemented. That does not affect interactive workspace collaboration, but it means that long-lived Managed Agents awakened by events are not a shipped capability.

## Choose operational ownership, not a feature checklist

QM suits a team extending personal agents into organizational collaboration: personal environments remain distinct, channels and projects share on demand, and engineers maintain the deployment layer and runtime.

CubePlex suits an organization that wants agents to become part of its team workflow: work begins with an entry point, members, permissions, and model policy; runs in a shared sandbox; and ends as an artifact the team can continue to use. For those teams, the important outcome is not another agent computer. It is agent work that does not disappear with one person, channel, or conversation.
