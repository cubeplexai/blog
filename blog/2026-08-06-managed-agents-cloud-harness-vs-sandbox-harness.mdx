A Managed Agent usually stores a prompt, model selection, and tool configuration. A platform must also decide which process owns the agent loop: which component keeps context, sends model requests, handles tool calls, enforces approvals, retries failed steps, cancels work, and resumes a run.

Two runtime architectures are common. One installs the harness inside every sandbox so that the agent loop and workspace run in the same isolated environment. The other runs the harness as a centralized cloud service that controls one or more sandboxes through APIs. Both isolate execution, but they create different lifecycle boundaries, failure domains, and scaling models.

## The harness runtime boundary

In this article, the harness is the software layer outside the model that advances an agent run. It typically performs these functions:

- assemble the system prompt, conversation history, skills, and memory;
- send model requests, parse tool calls, and return observations to the model;
- manage context compaction, token budgets, retries, cancellation, and human approval;
- bind tools such as shells, files, browsers, MCP servers, and subagents;
- record run events, traces, costs, and final artifacts.

The phrase “agent runs in a sandbox” does not identify the harness boundary. If the model loop remains in a cloud service and the sandbox only accepts commands and returns results, the system still uses a centralized harness. A harness is sandbox-local only when the process that owns context and advances model turns also runs inside the sandbox.

[OpenHands Runtime documentation](https://docs.openhands.dev/openhands/usage/architecture/runtime) describes a centralized implementation: the backend produces an action and sends it over REST to an Action Execution Server in a container, which executes the action and returns an observation. The [OpenAI Agents SDK SandboxAgent guide](https://openai.github.io/openai-agents-python/sandbox/guide/) similarly has a `Runner` prepare the agent, bind a sandbox session, and advance model turns while the sandbox supplies the workspace and tool execution.

On the other side, [OpenAI's description of Codex cloud](https://openai.com/index/introducing-codex/) says that each agent runs in a separate cloud container. [Claude Code Action](https://github.com/anthropics/claude-code-action) places the Claude Code runtime on a GitHub runner and accesses the model service from that runner. These implementations are closer to a sandbox-local harness.

This article treats a sandbox as an isolated execution resource that supplies commands, files, processes, and state lifecycle. It does not repeat the comparison between container, Kubernetes, and MicroVM resource models. For scheduling, pause and resume, and snapshot semantics across sandbox implementations, see [OpenSandbox vs. CubeSandbox: Choosing Between Kubernetes Resources and a MicroVM Runtime Stack](./opensandbox-vs-cubesandbox-agent-platform-selection).

## Sandbox-local harness

This architecture packages the agent CLI, model client, context state, and tool execution environment into the same sandbox.

The harness can call a local shell, read files, and connect to a PTY or browser without defining a remote protocol for every action and observation. Existing tools such as Codex CLI, Claude Code, OpenClaw, or an internal CLI can be placed into an image with fewer changes. Local calls also reduce RPC overhead, serialization, and large-result transfer for file scans, code indexing, browser screenshots, and long-running terminal processes.

The same packaging model is convenient for delivery into a customer VPC or edge environment. A platform can ship an image with a fixed harness version and dependencies while the customer supplies compute and model access. Pinning the image, harness, and workspace versions together makes an individual run easier to reproduce.

The tradeoff is tighter coupling between the agent and sandbox lifecycles. When an agent waits for human approval, a scheduled wake-up, or an external event, the platform must retain the sandbox or persist the workspace, processes, and harness state together. A filesystem snapshot alone cannot restore an active model loop. A recovery point may also need conversation state, pending tool calls, PTYs, and local services.

Running the harness inside the sandbox also creates a credential problem. Model requests require an API key or gateway token, and MCP servers or external systems may require additional credentials. If untrusted code in the sandbox can inspect the harness process environment, configuration files, or local sockets, the isolation protects the host but not the harness credentials. Production implementations usually need short-lived, task-bound model gateway tokens while keeping high-privilege approvals and long-lived secrets outside the sandbox.

Carrying a complete harness in every sandbox increases image size, cold-start content, and version-management cost. A long-paused sandbox can remain on an old harness version. Security fixes may require rebuilding, migrating, or forcibly terminating those instances.

## Centralized cloud harness

A centralized architecture runs the agent loop in a managed service. The sandbox supplies isolated compute, files, browsers, and process APIs, but it does not decide the agent's next action.

The harness does not depend on the lifetime of one sandbox. Conversations, memory, budgets, approval state, and run events can remain in the control plane while sandboxes are created, paused, released, or replaced for each task phase. An agent can release compute while waiting for user input. When work resumes, it can reconnect to the original sandbox, create a new instance from a snapshot, or select another image, region, or hardware profile.

This separation supports more flexible sandbox lifecycle policies:

- use a general-purpose CPU sandbox for code changes and allocate a GPU sandbox only for training or inference;
- separate an authenticated browser environment from the code execution environment, with distinct network and credential policies;
- run high-risk tools in a disposable sandbox and destroy it after use;
- retain the agent trajectory after a sandbox failure and recreate the execution environment from the most recent persisted observation;
- release continuously running compute while the agent waits for an approval, timer, or webhook.

A centralized harness can also let one agent control multiple sandboxes at the same time. A coding agent can create three workspaces for competing fixes, run tests in parallel, and compare the results in the control plane. A research agent can assign different data sources to isolated environments. A testing agent can run operating-system, dependency, or browser combinations concurrently. The sandbox becomes a compute resource that the agent leases, uses, and releases rather than the machine where the agent permanently lives.

Multi-sandbox concurrency has its own cost. The harness must keep branch state, resource leases, and budgets for each path, then handle partial failures, timeouts, cancellation, and result merging. When two sandboxes modify the same repository, the platform also needs explicit rules for branches, artifacts, and final commit integration. Without those controls, more sandboxes only increase cost and uncertainty.

![Sandbox lifecycle and parallel orchestration under a cloud harness](/img/blog/managed-agents-architecture/control-plane-multi-sandbox-en.svg)

The primary cost of this architecture is the remote execution protocol. Shells, files, PTYs, browsers, and streaming logs must all be represented through APIs. Small file reads and short commands incur more round trips. Large observations need truncation, compression, or object-storage references. A network interruption can also leave the harness out of sync with a running sandbox, so execution APIs need idempotency, leases, heartbeats, reconnection, and explicit command states.

The control plane becomes a shared multi-tenant failure domain. The harness service must limit each agent's concurrency, context memory, model requests, and event writes so that a runaway task cannot exhaust a worker. Centralization does not provide reliability by itself. It places recovery, audit, and policy enforcement in one service that can implement them consistently.

## Lifecycle and failure recovery

The clearest distinction between the architectures is whether “the agent still exists, but its sandbox does not” is a normal state.

| Runtime state | Sandbox-local harness | Centralized cloud harness |
| --- | --- | --- |
| Waiting for human approval | Retain the sandbox, or snapshot both harness and workspace before stopping | Persist the pending action in the harness; the sandbox can be released |
| Waiting for a timer or external event | Pause the complete runtime, or have an external service restart it | Keep agent state in the control plane and lease a sandbox when the event arrives |
| Sandbox process failure | The harness and tool environment may fail together | Retain the trajectory and reconnect to or create a sandbox |
| Harness worker failure | Local sandbox state may remain, but an external system must detect and take over the run | Recover on another worker from an event log, checkpoint, and lease |
| Environment upgrade | Harness and sandbox image usually upgrade together | Harness and execution images can roll out and roll back independently |
| Long-running cost | Idle agents still require storage for the complete sandbox state | Control-plane state and compute resources can be billed and reclaimed separately |

[Kubernetes Agent Sandbox](https://kubernetes.io/blog/2026/03/20/running-agents-on-kubernetes-with-agent-sandbox/) describes an agent workload as a stateful singleton with a stable identity that can remain idle for long periods and resume after a pause. That model fits a sandbox-local harness, but it also shows the additional requirements: the sandbox is no longer an ordinary short-lived container. It needs stable network identity, persistent state, warm pools, and scale-to-zero behavior.

A centralized harness is closer to a distributed workflow system. It must record intent before executing a command, advance state after receiving an observation, and use idempotency keys to distinguish “the command did not run” from “the command ran but its response was lost.” Otherwise, reconnecting a sandbox can duplicate a message, commit, or external API call.

## Security boundaries and credentials

Both architectures must handle prompt injection, tool abuse, and credential escalation. The difference is whether high-value credentials enter the execution environment.

A sandbox-local harness usually needs at least model-service access. Injecting a long-lived API key allows code running in the sandbox to read and exfiltrate it. A safer implementation gives the harness a short-lived token for a centralized model gateway, where the platform enforces model allowlists, quotas, user attribution, and audit. External tool credentials should also be exchanged for each tool call rather than stored as long-lived environment variables.

A centralized harness can keep model keys, approval rules, and long-lived credentials in the control plane while giving the sandbox only the minimum permission required for one command. The harness still consumes untrusted repository content, webpages, and tool results. Indirect prompt injection can induce it to call privileged tools through its legitimate identity. Security depends on independent constraints around tool permissions, network egress, and approvals, not only on whether the harness runs outside the sandbox.

NIST's guidance for agentic AI discusses workflow-bound credentials, continuous authorization, agent segmentation, and complete telemetry. These requirements apply to both architectures, though a centralized control plane can usually enforce them more consistently. [NIST Agentic AI Security](https://csrc.nist.gov/csrc/media/presentations/2026/agentic-ai-emerging-threats%2C-mitigations%2C-and-cha/1.3-agentic_ai-sotiropoulos.pdf)

## Where each architecture fits

| Dimension | Sandbox-local harness | Centralized cloud harness |
| --- | --- | --- |
| Tool calls | Direct access to local shells, files, PTYs, and browsers | Depends on a remote execution protocol and observation transport |
| Sandbox lifecycle | Usually bound to the agent run | Can be leased, released, and replaced by task phase |
| Multiple sandboxes | Requires the harness to hold remote scheduling credentials, increasing complexity | One agent can directly manage multiple resource leases |
| Model and tool credentials | Must enter the sandbox or be obtained through short-lived gateway tokens | Long-lived credentials can remain in the control plane |
| State recovery | Must recover harness state and workspace together | Harness checkpoints and sandbox snapshots can recover independently |
| Version upgrades | Harness version follows the image and existing instances | Harness and execution images deploy independently |
| Customer VPC or edge | A self-contained image is easier to deliver | Requires a reliable channel between the control plane and customer environment |
| Multi-tenant governance | Per-instance isolation is direct; policy distribution is more complex | RBAC, budgets, audit, and approval are easier to centralize |
| High-concurrency scaling | Every agent starts a complete harness | Harness workers and sandboxes can scale separately |

A sandbox-local harness fits self-contained CLIs, a single long-lived workspace, customer-VPC deployments, and workloads dominated by local tool interaction rather than cross-environment scheduling. A centralized harness fits long waits, event-driven runs, unified compliance controls, phase-specific execution environments, and parallel work across multiple sandboxes.

The two architectures can also be combined. The control plane keeps the Managed Agent definition, version, identity, approvals, and durable state. A restricted worker in the sandbox handles PTYs, file indexing, browser control, and batched local operations. The worker can execute one structured step and return the result without holding long-lived model credentials or becoming the only copy of agent state. This split preserves tool locality without binding the full Managed Agent lifecycle to one sandbox.

## CubePlex architecture direction

CubePlex uses a centralized harness with independent sandboxes. The CubePi agent loop, context, middleware, MCP routing, approvals, streams, and traces are managed by the cloud control plane. Sandboxes provide isolated shells, files, browsers, and artifact execution environments.

This choice separates the Managed Agent lifecycle from its execution environment. An `AgentDefinition` and its immutable versions should be stored independently of any sandbox. When a conversation, scheduled job, trigger, or IM message references the same Managed Agent, the control plane resolves a fixed prompt, model, skills, MCP configuration, and permissions before allocating an execution environment for that run. An agent does not need to retain a sandbox while waiting for input or an event.

Multi-sandbox scheduling follows from the same boundary. A Managed Agent should not be modeled as one permanently assigned machine. The control plane can create isolated workspaces for subagents or parallel branches, aggregate results in the harness, enforce budgets, and reclaim resources. Each sandbox can use a different image, network policy, or hardware profile.

This boundary does not require every tool operation to return to the control plane individually. A restricted execution worker inside the sandbox can handle PTYs, code indexing, browser recording, and large-file processing to reduce high-frequency RPC and large observation transfers. The control plane still owns the agent trajectory, long-lived credentials, approval state, and final audit record.

This article describes CubePlex's architecture direction. CubePlex currently uses a centralized CubePi run path with independent sandboxes. Managed Agent definitions and one-to-many sandbox orchestration have not yet been delivered as complete product capabilities. The next step is to fix each Managed Agent's version, runtime identity, and audit context in the control plane, then treat sandboxes as execution resources that can be leased, replaced, and scheduled in parallel for each task. The agent persists; sandboxes are used on demand. That lifecycle boundary is the main reason CubePlex chose a centralized harness.
