Dify composes Workflows, Chatflows, Knowledge, and New Agents in Studio, then publishes a web app, API, embed, or MCP entry ([dify.ai](https://dify.ai/), [Publish](https://docs.dify.ai/en/self-host/use-dify/publish/README)). What lasts is App config, Chatflow/Workflow draft→publish versions, and a reusable New Agent capability object. CubePlex is a self-hosted team Agent Workspace: Persona, Skills, MCP, and layered memory sit on the Workspace; each Workspace keeps a sandbox whose files, packages, and worktree survive restarts; web and IM bridges enter the same Workspace identity ([cubeplex.ai](https://cubeplex.ai/), [cubeplexai/cubeplex](https://github.com/cubeplexai/cubeplex)). Both can self-host. Choose by which object you need to persist: a publishable App / Agent capability, or a Workspace Agent plus worktree the team keeps using.

## App, Workflow versions, and New Agent

Studio wires model calls, retrieval, tools, branches, and human confirmation. A Workflow runs from trigger to finish; a Chatflow adds a conversation layer on the same nodes; Triggers attach only to Workflow ([Workflow & Chatflow](https://docs.dify.ai/en/self-host/use-dify/build/workflow-chatflow)). Knowledge is a first-class RAG object: Owner/Admin/Editor create it; visibility is set on the knowledge base ([Knowledge](https://docs.dify.ai/en/self-host/use-dify/knowledge/readme)).

Version control today covers Chatflow and Workflow only: Current Draft stays off live traffic; Publish Update promotes the draft to Latest Version; earlier publishes remain as Previous Versions; Restore loads an old version into draft and requires another Publish to go live ([Version control](https://docs.dify.ai/en/self-host/use-dify/build/version-control)).

**New Agent** (beta) is a first-class product object with its own config and lifecycle: ship it as a standalone chat app, or drop it into a Workflow as an Agent node. Capability (model, prompt, skills, files, tools, env vars) is separate from task (user message or node instruction). Edits autosave as draft; Publish makes a version live; version history can restore, and restoring also restores Build-time persistent sandbox files. DSL export reattaches library skills by name; embedded skills and files are not included ([New Agent overview](https://docs.dify.ai/en/self-host/use-dify/build/new-agent/overview), [Build](https://docs.dify.ai/en/self-host/use-dify/build/new-agent/build), [Introducing New Agent](https://dify.ai/blog/introducing-new-dify-agent)). Creating or managing agents requires Editor or above.

The Agent node exists in Workflow apps only, not Chatflow. Two nodes that invite the same published agent still get separate sandboxes; files and tool installs from one node run do not carry to the other — pass data through declared outputs. Task variables passed as text truncate at 2,000 characters; longer content must go as a file ([Agent node](https://docs.dify.ai/en/self-host/use-dify/nodes/agent)).

## Workspace Agent, layered memory, and durable worktree

In CubePlex, what lasts is the Agent on a Workspace: AgentConfig holds Persona; Skills and MCP connectors attach to the Workspace; personal / Workspace / organization memory are layered. Members coming from web or IM meet the same role setup and approvals — switching a Slack channel does not invent a new Persona. The IM entry only scopes the session (one-to-one DM, shared or isolated group routing, and so on); it does not redefine the Agent.

Each Workspace has a sandbox: files, packages, and worktree survive process restarts. The agent loop runs on the control plane; the sandbox is a rentable execution environment still under org and Workspace roles and approvals. Another member can open the same Workspace without rebuilding state from someone’s private chat.

CubePlex does not treat “publish as an external App” as the default delivery shape. Default delivery is Workspace state the team can keep editing and running.

## Code-node sandbox, New Agent sandbox, Workspace sandbox

Do not collapse these into “Dify has a sandbox.”

The **Code node** runs deterministic Python/JS transforms. Docs: code executes in a strict sandbox that prevents filesystem access, network requests, and system commands; outbound traffic goes through an SSRF proxy, and network can be disabled ([Code](https://docs.dify.ai/en/self-host/use-dify/nodes/code)). The Compose service is `sandbox`, in the lineage of the earlier DifySandbox OSS component. It serves a pipeline step, not a daily CLI workbench.

The **New Agent sandbox** deliberately opens the other door: run commands, install programs, read and write files, on a model-driven ReAct + Bash path ([overview](https://docs.dify.ai/en/self-host/use-dify/build/new-agent/overview), [why we redesigned](https://dify.ai/blog/why-we-redesigned-dify-agent)). Compose uses a different service set: `agent_backend`, `local_sandbox`, `agent_ssrf_proxy`, gated by flags such as `NEXT_PUBLIC_ENABLE_AGENT_V2`. Missing services or a compose file older than the images shows up as a missing Agents page or immediate run failures ([Docker Compose](https://docs.dify.ai/en/self-host/deploy/quick-start/docker-compose), Build troubleshooting).

Persistence splits on Build vs published runs ([Build](https://docs.dify.ai/en/self-host/use-dify/build/new-agent/build)):

| Context | Files and CLI installs |
| --- | --- |
| Build mode | Persistent by default — part of agent setup for later chats and workflow runs; mark Temporary to clear when the build chat ends |
| Published run | Always temporary — “nothing that happens in a run changes the agent itself” |
| Tools list | Tools installed in Build can remain after publishing; installs during a published run stay temporary |

Capability (prompt, skills, tools) changes only in Configure / Build; end users cannot change a published agent’s prompt/skills/tools even if they ask in natural language. Discarding Build drops config changes and persistent files from that build chat.

Published runs and every access point share hard caps: default 1-hour run timeout (`APP_MAX_EXECUTION_TIME`, `WORKFLOW_MAX_EXECUTION_TIME`, `DIFY_AGENT_RUN_TIMEOUT_SECONDS`); at most 500 model requests per run; reply files default to 50 MB; the sandbox proxy blocks private-network addresses — intranet material must be added to Files first.

**Community isolation** (repeated on overview, build, and Agent node): Community Edition uses **file-access controls** to limit cross-conversation filesystem access when the same agent is exposed to multiple end users. Those controls reduce risk; the Agent runtime is **not intended** to provide a hardened security boundary between mutually untrusted users or workloads. For strong isolation, docs point to separately hardened infrastructure or Cloud / Enterprise.

**Enterprise** has a separate deployment path. Marketing copy says every session runs in a dedicated sandbox container with process, filesystem, and network isolation, non-root, and custom network policies ([why we redesigned](https://dify.ai/blog/why-we-redesigned-dify-agent)). Enterprise 3.12 docs describe the default as one dedicated Pod per Agent session (warm pool; reclaim on end or idle). With `sandboxGateway.enabled: false`, sessions fall back to a shared long-running runtime; docs state isolation is weaker and treat that mode as fallback only ([Agent Sandbox Deployment](https://enterprise-docs.dify.ai/en/3.12.x/deploy/advanced-configuration/agent-sandbox)). Whether Community `local_sandbox` is “one shared container for all sessions” is not stated in public docs; quantify only the service names and the file-access notice above.

**CubePlex Workspace sandbox** belongs to the Workspace, not to a Studio publish version. Files, packages, and worktree persist across restarts for the team to keep editing; the control plane holds the agent loop. The question it answers is whether the team worktree is still there — not whether this App run’s temporary FS survived. Isolation and multi-tenant threat models depend on how the deployer places nodes and network; the product emphasizes org / Workspace roles and approvals rather than importing Community’s file-access notice wholesale.

## Studio’s four roles vs org / Workspace roles

Community ships four built-in roles ([Team members](https://docs.dify.ai/en/self-host/use-dify/workspace/team-members-management)):

| Role | Access |
| --- | --- |
| Owner | Full control; one per workspace |
| Admin | Members and model providers, plus everything Editor can do |
| Editor | Create / edit / delete apps and knowledge bases; **required to manage Agents** |
| Normal | **Use published apps only** |

Custom roles and fine-grained app / knowledge access are documented under Enterprise. Community collaboration is workspace-scoped “Editors build and publish, Normals consume” — there is no separate Community “publisher” role. Pricing marks Community freemium as Single Workspace; Multiple Workspaces, SSO, fine-grained RBAC, and unlimited App logs sit in Enterprise packaging ([pricing](https://dify.ai/pricing/dify-enterprise), [dify-enterprise](https://dify.ai/dify-enterprise)). Community App Logs History is 30 days; the official New Agent blog states log archives are not available in Community Edition.

CubePlex’s open-source package ships organization and Workspace roles, model policy, approvals, and usage. Default collaboration is multiple people on one Workspace Agent; permission sits on org / Workspace, not on “who published which App.” Web and IM bridges (Slack and others) enter the same Workspace identity: a channel change only scopes the session; it does not change Persona / Skills / MCP bindings.

## Where Dify Community fails as a team daily Workspace

These conditions come from docs and packaging, not invented product bugs:

1. **Untrusted multi-user isolation.** Community Agent runtime is explicitly not a hardened boundary. Using one New Agent as a shared “daily desktop” for hostile or strongly isolated tenants contradicts the stated threat model.
2. **Published runs cannot accumulate environment.** CLI installs and work files in live sessions are temporary by default. “Leave the environment better than you found it” requires someone to return to Build, Apply, and Publish again.
3. **Shared-agent blast radius.** When one published Agent is invited into many Workflow nodes, capability updates hit every consumer. Access Points help surface impact; Community has no resource-scoped RBAC for “use Agent X but not Y.”
4. **Coarse roles.** Only Editor+ can manage Agents; Normal cannot co-edit. Per-resource grants need Enterprise.
5. **No New Agent node in Chatflow.** Conversational daily entry is a standalone Agent app, or a Chatflow without a New Agent node.
6. **Hard caps.** 1-hour kill, 500 model calls, 50 MB reply files, 2k-character task text. Long collaboration needs env retune or task splitting.
7. **Network posture.** Agent sandbox cannot fetch intranet by default; Code node forbids shell / FS by design. Needing both “safe code transforms” and “full CLI + private nets” fights the product split.
8. **Observability ceiling.** 30-day App logs; no log archives; audit / SIEM live in the Enterprise story.
9. **Single Workspace packaging.** Multi-BU isolation and tenant quotas are the Enterprise multi-Workspace story.
10. **Beta and DSL gaps.** New Agent is labeled beta; embedded skills/files stay out of DSL — team handoff needs a side channel.

## Where Dify wins as an App Studio

The same docs show where Dify is strong:

- **Visual agentic workflows.** Models, tools, logic, checkpoints, and fallbacks on one canvas; Workflow vs Chatflow roles are clear.
- **Publish once, many surfaces.** The same published config feeds web app, API, embed, and MCP.
- **First-class Knowledge / RAG.** Retrieval node, vector / full-text / hybrid, rerank, metadata filters.
- **Code node for controlled transforms.** Sandboxed Python/JS with retries and error handling — good pipeline hygiene, not a daily CLI Workspace.
- **New Agent as reusable capability + Workflow step.** Single source of truth for Capability; per-node Agent Task; declarative outputs; Logs with access-point attribution.
- **Build mode.** Non-prompt engineers can shape agents by chatting; skills package methods; tools are governed workspace integrations.
- **Upgrade ladder when isolation matters.** Dedicated sandbox Pods, SSO, fine-grained RBAC, audit — paid / Enterprise path, not Community defaults.

When those conditions hold, pick Dify (Community or cloud) instead of forcing CubePlex. You need a publishable App, versionable Workflows, and Agent capability hung on Studio objects.

CubePlex fits a narrower, harder set: platform or engineering teams that must self-host; multiple people sharing one Workspace Agent over time; files and packages that must survive restarts in a worktree; IM and web under one identity and approval model, where a channel switch must not switch Persona. Studio draft/publish and “published runs are always temporary” block that path directly.

One organization can split traffic: callable apps on Dify; the daily team workbench on CubePlex. The persistent objects differ — even when both are in use, cut on object boundaries and do not treat a New Agent sandbox as a Workspace worktree.
