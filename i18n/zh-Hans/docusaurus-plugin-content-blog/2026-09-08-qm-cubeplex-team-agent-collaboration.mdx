QM 证明了一件事：公司里的 Agent 不能只是一群共用 Slack bot 的个人助手。YC 在内部部署数十个个人 Agent 后，把 memory、文件、凭据视图、权限、定时任务和持久 sandbox 收进 scope。个人、频道、项目和组织各自拥有边界，需要共享时再 grant。这个设计解决的是如何让大量 Agent computer 同时为一家公司工作。

CubePlex 的出发点不同。团队通常不缺一个可以执行命令的 Agent，而是缺少一处能持续推进工作的地方：成员替换后，资料、连接器权限、工作文件和中间产物仍然可用；同一项工作可以从聊天入口进入，在 Sandbox 中完成，并留下其他人可继续修改和复用的交付物。CubePlex 因此以 Workspace 而不是个人 Agent computer 作为协作单元。

## QM 解决的是 Agent fleet 的边界

QM 的 scope 是一个严肃而必要的设计。员工的个人 Agent 不应默认看到同事的文件或凭据；频道需要共享上下文，但不应因此获得组织里每个人的环境。QM 的 headless core 负责身份、策略、调度和 agent loop，`execute` 将命令发送到对应 scope 的持久 sandbox。Slack、Web 和管理界面都是这个 core 之上的 surface。

这让技术团队可以把 Agent 当作一批可定制的工作电脑来运营。组织特有的工具、Skill、sandbox 镜像和基础设施放在 deployment directory；需要深度定制时，还可以维护私有 fork，同时让 core 跟随上游。对已经有平台工程团队、希望把运行环境和组织定制完全留在自己代码库中的公司，这个边界很有吸引力。

它也明确了采用成本。部署 QM 不等于安装一个聊天应用：团队需要决定云账号、身份、模型凭据、网络、镜像、升级和事故处理由谁负责。QM 当前公开 README 也将其定位为面向 startup 的自托管 harness。Kubernetes sandbox 后端仍在公开 PR 中，描述里明确写着真实集群验证尚未完成；同一时期的 PR 与 issue 仍在处理外部内容筛选、凭据传递和审计记录等运行细节。这里没有“谁更先进”的结论，只有一个实际问题：公司是否准备好运营一支 Agent fleet。

## 团队工作不会随着个人 Agent 一起结束

一次竞品研究、发布准备或客户方案，往往会经过多个成员。有人从飞书或 Web 发起任务，有人补充资料，有人让 Agent 在代码库、文档和网页之间查证，最后需要审阅并交付文档、表格、图片或代码。真正需要长期保留的不是某个 Agent 的对话，而是这项工作的上下文和结果。

CubePlex 把这组资产放进同一个 Workspace：成员和角色定义谁参与；Workspace sandbox 保存文件、包和工作树；个人、Workspace、组织三层 memory 分别保存个人偏好、团队事实和组织知识；MCP connector 按 Workspace 授权；生成的文件、预览、代码和图片以 Artifact 留在对话中。成员离开、入口切换或下一轮任务开始时，团队仍在同一处继续这项工作。

这不是把所有数据粗暴地汇总到公司级 Agent。个人 memory 仍保留个人范围，连接器也需要明确授予 Workspace。差别在于，团队共享的默认对象是为一项工作建立的 Workspace，而不是先创建许多个人或房间 scope，再把共享关系逐一拼出来。

## Runtime 是执行资源，不是协作的主人

两套系统都把 Sandbox 与模型循环分开。QM 把每个 scope 的 sandbox 作为该 scope 的持久 computer；CubePlex 的 Agent runtime 基于 CubePi，在服务侧负责多模型访问、工具执行、流式输出、中间件和 durable checkpoint，Workspace sandbox 则保存执行所需的工作状态。v0.7.2 的 `RunManager` 在服务侧构建并驱动 agent，再将 sandbox 作为执行依赖传入。

这一层的取舍会直接影响团队日常使用。把 sandbox 绑定到个人或频道，适合希望每个 scope 都拥有独立 computer 的组织；把 sandbox 绑定到 Workspace，适合把代码、资料、Skill 和产物留给一个项目组持续使用的团队。CubePlex 的运行时和 sandbox 可以部署在 Docker Compose 或 Kubernetes 上，但用户不需要为了每个组织维护一份 QM deployment repository，才能获得 Workspace、角色、模型策略、成本跟踪和多入口协作。

CubePlex 已提供按计划或 webhook 执行的自动化触发器；当前 trigger pipeline 只运行 `inline` target，`managed_agent` target 尚未实现。这个限制不影响 Workspace 内的交互式协作，但它意味着长期复用、由事件唤醒的 Managed Agent 还不能作为已交付能力承诺。

## 选择的是运营责任，而不是功能清单

QM 适合把个人 Agent 扩展为组织协作的团队：个人环境先独立，频道和项目按需共享，并由工程团队维护部署层和运行环境。

CubePlex 适合希望直接把 Agent 纳入团队工作方式的组织：一项工作从入口、成员、权限和模型策略开始，在共享 Sandbox 中执行，并以团队可继续使用的 Artifact 结束。对这类团队，关键不是再增加一台 Agent computer，而是让 Agent 的工作不再随着某个人、某个频道或一次对话而散失。
