2026 年 7 月，Y Combinator 把内部使用的 [QM（Quartermaster）](https://github.com/yc-software/qm) 以 MIT 许可证放到公开仓库 `yc-software/qm`。仓库创建时间为 2026-07-29；下文源码与文档核对到提交 `95b5a6a`。

QM 面向 startup：每个员工有隔离的工作现场；需要协作时，在频道、群消息和项目里跟 agent 一起干活。它默认切开「人」与「房间」的边界，共享靠显式授权。个人助手被整公司共用时，记忆、凭据和副作用容易缠在一起——QM 的协作模型按这个前提展开。

## 个人助手进入公司时会撞在哪里

个人助手通常绑在一个人的对话、本机目录和登录态上。同一套现场交给多人共用，冲突会很快出现。

项目知识与私人偏好落在同一份记忆和文件里，事后分不清归属。凭据进入共享执行环境后，很难说明是谁在用、用了什么。频道协作又需要共同上下文：各自重建现场的成本过高。公司侧还要统一可用的模型与 harness，以及可审计的副作用。

README 把 QM 写成给 startup 用的 multiplayer harness：员工互不影响地独立工作，也可以在频道、群和项目里协作。

## 协作模型：个人现场与房间会合

QM 用 scope 表示工作边界，包括 personal、channel、team、org、group；项目落到 group 一类 scope。每个个人和每个房间可以各自持有 memory、文件、keychain 视图、权限、cron、web app，以及 durable sandbox。

协作默认不共享全量现场。Skills 归某个 scope 所有，通过 grant 分享；升到全 org 要管理员把关。员工可以把 agent 调成「自己的」，同时在 Slack 频道和项目里使用同一套身份与配置。Slack 与 Web 之间身份连续。

安全叙事跟 OpenCode、Codex、Claude Code 一类本地 coding agent 对齐：agent 作为它所服务的那个人行动，带上该人的凭据与权限，动作可审计。组织再选一种安全姿态，更窄的 scope 只能加严。命令策略在各种姿态下都存在；威胁模型、运维假设和已知限制写在 `SECURITY.md`。

## 架构上的几处后果

协作切分会落到几处实现选择。

回合走 headless core：身份、策略、调度和 agent loop 集中在这里，持久化在 Postgres。Pi、OpenCode、Codex、Claude Code 都可以驱动同一套 core。Agent 工具面相对固定；`execute` 在该 scope 自己的隔离 sandbox 里跑命令，安装过的工具会留下来，成为这个 scope 的 durable computer。

Web UI、Admin、Portal 是挂在 core HTTP API 上的可选插件。Slack 是 core 启动并直接监督的进程内插件。通用 core 保持公司无关；org 配置、自定义 tools/skills、sandbox 镜像和基础设施放进部署目录，由 `qm init` 落到运营方自己的云账号。

浏览器路径与 shell 门禁分开：browser runner 内的动作不再进入 command policy 或人机审批，依赖任务级同意与花费检查，流量走 browser provider，而不是 QM 的 egress proxy。

## SECURITY.md 写明的边界

QM 自述为 early、experimental，不是硬化的公有或多租户服务边界。已知限制包括：命令策略可被混淆、编码或「先写后执行」绕过，官方称为 speed bump；sandbox 内使用中的凭据是明文；内容筛选不完整且偏启发式；管理员可读敏感内容（有审计，但不另开一层用户同意）。

部署前需要按具体环境做安全与运维审查。文档里的设计目标不能直接当成已经兑现的保证。

已以 Slack 为日常协作面、能在自有云上运维、并接受实验性软件的团队，可以从依赖 `@yc-software/qm` 的组织部署仓库和仓库内部署文档入手。本文不写逐步教程。
